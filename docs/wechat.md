# 微信群回复（第二阶段，不挡住核心）

核心是「任意 MCP Agent 能点、能滑、能打中文」。微信只是一个 skill，用来证明这件事够用。不把微信写进固件，也不写进 `phone.py`。

## 全自动

按 seven 的选择，代码里没有草稿，也没有「等我点确认」。`skills/wechat-group-reply/SKILL.md` 是回复内容的唯一约束：语气、话题、禁词、时段都改那个文件。

## 系统熔断（skill 关不掉）

- 熔断是协作的。Agent 要自己调用 `skill_check` / `skill_confirm_send`；普通的点、滑、打字不会自动停。
- 屏幕上出现「操作频繁」「风控」「验证码」，或 skill 里 `extra_stop` 的词：立刻停，不要重试。这次跳闸记在数据目录的 `guard.json` 里，重启服务还在。看过手机、确认提示已经没了，再删掉这个文件。代码里没有给 Agent 用的解除工具。
- 默认两次发送至少间隔 8 秒，每小时最多 20 次，23:00–07:00 不发。skill 不能把间隔改到 3 秒以下，也不能把每小时改到 30 次以上。
- 发送之前调用 `skill_prepare_send`。频率和静默不过，就不要按发送。这一步不计入次数。
- `skill_confirm_send` 的 `bubble_visible` 只是调用方的声明。服务端看不见屏幕，不能证明气泡是真的。输入框清空和串口 `ok` 都不算发送成功。计数发生在频率和静默再次通过之后。
- 一旦熔断，所有会发出 HID 的接口都拒绝，只剩状态、截图和显式重置。重启不会解除。

## 风险

用专用运营号，不要用主号。自动化操作可能违反微信条款。行为太像机器（秒回、全天、群发、话术重复）仍可能被限制。截图会进入你正在用的视觉模型，群聊内容会离开本机，自己衡量要不要这么做。

## 以后怎么接别的客服

在 `skills/` 里加一个目录，放 `SKILL.md`，需要固定坐标再放 `layout.json`。Agent 读 skill，用现有的点、滑、打字工具。不用改固件，不用改核心服务。`skills/customer-service/SKILL.md` 是占位，不是完整业务。
