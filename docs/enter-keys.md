# Enter 的发送、导航与换行

默认把未知用途的 Enter（包括组合键）作为可能发送消息处理，执行发送间隔、每小时额度和静默时段限制。调用方写一个 `navigation: true` 不能绕过这些限制。

需要在搜索、导航或换行时按 Enter，先调用 `GET /api/control/observe`，再单独提交：

```json
{"text":"enter","screen_id":"刚获取的 screen_id","enter_intent":"navigation"}
```

提交到 `POST /api/key`；也可向 `POST /api/control/action` 增加 `"action":"key"`。换行使用 `"enter_intent":"editing"`。这两种用途需要安装可选 OCR 依赖，必须能看见屏幕键盘；硬件键盘隐藏了屏幕键盘时不能自动证明用途。

服务器自己识别同一排的空格键、123/ABC 切换键，以及右下角的明确操作标签。导航支持「搜索」「前往」「下一项」「下一步」「完成」及 Search/Go/Next/Done；编辑支持明确的「换行」/Newline。不把含义不确定的 Return 标签或 Shift+Enter 自动当作换行。识别不到完整证据时拒绝该非发送请求，不发送按键。

证据只允许当前任务中的一次 Enter。OCR 前后及实际写入 HID 前都检查画面新鲜度、同一画面内容和连接代次；证据三秒后过期。任何画面变化都要求重新观察，避免旧键盘或旧焦点证据误用于聊天框。非发送 Enter 不占发送额度，不消费已有发送预留，也不增加待确认消息数；熔断仍会阻止它。

最后一次证据校验到 HID 写入全程持有画面发布锁，视频线程不能在中间替换键盘画面。
没有发布锁的画面后端（目前包括 UxPlay）拒绝免额度请求；普通 Enter 仍按发送限制处理。

导航/换行 Enter 不能放进 batch：前面的动作可能已改变输入焦点。逐步获取新观察后执行。发送消息仍使用原有准备发送、实际发送、确认新消息气泡的流程；不要为导航或换行调用 `confirm-send`。

这是保守的视觉判定，需要真机核对 iOS 键盘布局和硬件 Enter 的实际行为。自定义键盘、看不见键盘、OCR 不确定或应用没有可靠的操作标签时，保持未知用途的发送限制。
